# Firmware Update (OTA) and HIL Simulation Strategy

This document outlines the planned architecture for performing safe Over-The-Air (OTA) updates on the dual-board ESP32-S3 setup, as well as the strategy for Hardware-in-the-Loop (HIL) simulation using the native USB interface.

## 1. Dual-Board Safe OTA Update Architecture

The product relies on two ESP32-S3 microcontrollers:
- **Master Board:** Handles sensor reading (I2C), MIDI logic, and USB communication.
- **Slave Board:** Handles the Slint graphical user interface (GUI).

Because only the Master board has a physical USB connection to the host PC, the firmware update process requires a coordinated effort between the two boards.

### Partitioning & Failsafe
Both ESP32-S3 chips will be configured with an A/B OTA partition scheme (`ota_0` and `ota_1`) alongside an `otadata` partition. By leveraging the `esp-idf` OTA APIs, new firmware is always flashed into the inactive partition. If a boot failure occurs (e.g., watchdog timeout, panic), the bootloader automatically falls back to the previous healthy partition.

### Two-Step Update Process

1. **Master Update (Host -> Master via USB):**
   - The PC host software sends the Master firmware binary over a dedicated USB endpoint (e.g., a custom USB CDC interface or a dedicated SysEx MIDI protocol).
   - The Master receives the stream, writes it to its inactive OTA partition using the `esp_ota` API, validates the image, and reboots.

2. **Slave Update (Master -> Slave via UART):**
   - The PC host software sends the Slave firmware binary to the Master over USB.
   - **Recommended Approach (`esp-serial-flasher`):** The Master board is physically wired to the Slave's `TX`, `RX`, `EN` (Enable), and `BOOT0` pins. Instead of relying on the Slave's application layer to perform its own OTA update, the Master utilizes the `esp-serial-flasher` library (ported to Rust). The Master resets the Slave into its ROM bootloader mode and flashes the binary directly over UART.
   - **Advantage:** This method is practically unbrickable. Even if the Slave firmware is completely corrupted, the ROM bootloader is immutable, allowing the Master to always recover and flash the Slave.

## 2. Hardware-In-The-Loop (HIL) Simulation via USB UART

To thoroughly test the Theremin's logic (MIDI ADSR envelopes, Master-Slave UART protocol, etc.) without physically moving hands over the ToF sensors, we will implement a HIL simulation interface.

### USB Composite Device (MIDI + CDC)
The ESP32-S3 features native USB OTG. The firmware currently uses `TinyUSB` to act as a USB MIDI device.
We will configure the USB descriptor as a **Composite Device** exposing two interfaces simultaneously:
1. `USB Audio/MIDI` (for the DAW).
2. `USB CDC` (Virtual COM Port).

### Data Injection Workflow
- A simulation script on the PC (Python/Rust) opens the Virtual COM Port and injects serialized `Position3D { id, x, y, z }` events (the exact same structures generated by the YAML scenario player).
- On the Master ESP32, a dedicated thread listens to the USB CDC port.
- Using conditional compilation (`#[cfg(feature = "hil_sim")]`), the Theremin's main loop ignores real I2C interrupts from the VL53L4CD sensors and instead consumes events from the USB CDC queue.
- This allows deterministic, repeatable integration testing on the actual silicon.
